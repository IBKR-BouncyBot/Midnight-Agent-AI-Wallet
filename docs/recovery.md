# Private state and recovery

`services/runner/private-store.mjs` is an encrypted storage primitive; `services/mcp/journal.mjs` is an encrypted idempotency journal. `services/runner/payment-runner.mjs` composes the private store into a staged backend with process/restart tests. Its SDK adapter still requires trusted payment-construction and chain-observation callbacks; it is not a configured long-running wallet service. The live network test harness uses separate disposable encrypted SDK stores. The inspection MCP entry point has no live payment backend. See `runner-transaction-safety.md` for stage and integration details.

The private store preserves byte arrays and exact integer amounts, authenticates deployment context as AES-256-GCM associated data, and uses fresh nonces. Keep its random 32-byte storage key in a local secret store, separately from the encrypted file and backups. It is not a password. It does not derive or replace owner/agent authorization keys.

The runner must checkpoint **both** the last confirmed openings and the next candidate state, request identifier and exact serialized transaction before submission. Never overwrite confirmed state merely because proof generation succeeded. Once submitted, keep the transaction reference even if the HTTP response is lost. The request journal prevents a retry from automatically becoming a second submission.

Every open, restore or checkpoint disables the store's `canSpend` gate. Starting a new reconciliation also disables it immediately. A generation check prevents an older in-flight verifier from re-enabling spending after a newer checkpoint or verifier has been queued. The read-only `deploymentContext` exposes only the public deployment binding authenticated with the encrypted file; the runner validates it before giving private data to any recovery observer. A trusted chain verifier must reconcile the deployment, policy/state commitments, transaction outcome and coin qualification before enabling it. This callback boundary is implemented; its integration into a long-running submitter is still outstanding. A callback returning `true` without those checks is not a valid production implementation.

Export uses authenticated encryption; restore takes the exclusive writer lock before atomically publishing a complete file without overwriting an existing destination. This requires a local filesystem with hard-link support; failure leaves spending disabled. Restoration deliberately leaves spending disabled. A valid backup can still be old: compare its commitments and pending transaction records with the chain, recover the matching candidate, and resolve uncertainty before retrying. Do not reset idempotency history on restore. A stale backup without the private opening for the current commitment can mean funds cannot be recovered by this implementation.

The exclusive `.lock` is never removed automatically after a crash. Confirm that the previous runner has stopped, preserve a backup of encrypted state and the lock, then remove that exact stale lock and reopen. Never run two writers or use network shares. Native Windows has no directory-fsync support in this implementation; use a tested local Linux/WSL filesystem for a durable service and validate power-loss behavior. Current tests cover restart, wrong keys, tampering, wrong deployment, writer exclusion and preservation of pending candidates, **not** power loss.

Wallet seed recovery alone does not restore policy salts, coin openings, private accounting state, agent secrets or application request history. No mainnet recovery guarantee is made.
